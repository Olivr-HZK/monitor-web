# 前后端分离部署

前端（静态站）和后端（Node 服务）可以分别部署到不同域名/主机上，只要在构建前端时把「后端地址」写进去，并在后端配置允许该前端域名跨域即可。

---

## 一、整体思路

| 部分 | 部署位置示例 | 说明 |
|------|----------------|------|
| **前端** | GitHub Pages、Vercel、Cloudflare Pages、自建 Nginx 等 | 只提供静态文件（`dist`），不跑 Node。 |
| **后端** | Railway、Render、Fly.io、自建 VPS 等 | 跑 FastAPI（`backend/main.py`，uvicorn），提供 `/api/*` 接口。 |

用户打开的是前端页面，页面里的登录、AI 对话、玩法解析申请、受保护数据等请求会发到你配置的后端地址。

若你有 **Cloudflare 托管的域名**，希望把 API 暴露为 `https://api.你的域名` 并与静态站对接，见 **[Cloudflare域名与API公开访问](./Cloudflare域名与API公开访问.md)**（Tunnel、DNS、CORS 自检）。

---

## 二、前端：构建时指定后端地址

在**构建前端**的那台机器上，设置环境变量 **`VITE_API_BASE_URL`**（或兼容的 `VITE_API_BASE`），值为后端的**完整根地址，不要末尾斜杠**。

示例（后端已部署为 `https://monitor-api.example.com`）：

```bash
# 在项目根目录
VITE_API_BASE_URL=https://monitor-api.example.com npm run build
```

然后把生成的 **`dist`** 目录部署到你的静态托管（如 GitHub Pages、Vercel 等）。  
这样前端里所有 `/api/me`、`/api/login`、`/api/ai/chat`、`/api/data/xxx` 等请求都会发到 `https://monitor-api.example.com/api/...`。

- **不设置** `VITE_API_BASE_URL` 时：请求走**相对路径**（`/api/...`），适合「前后端同域」或「用 Nginx 反代把 /api 转到后端」的部署方式。

---

## 三、后端：允许前端域名跨域

后端代码里已通过 **`CORS_ORIGIN`** 控制允许的来源。

在后端所在的环境变量里设置：

```env
# 只允许你的前端域名（推荐生产环境使用）
CORS_ORIGIN=https://你的前端域名

# 示例：前端在 GitHub Pages
# CORS_ORIGIN=https://Oliver-HZK.github.io
```

不设置时默认为 `*`（允许任意来源），方便本地调试，生产建议改成具体前端域名。

后端部署的详细步骤（环境变量、Railway/Render 等）见 [后端部署说明.md](./后端部署说明.md)。

## 四、简要检查清单

1. **后端**已单独部署，并拿到可公网访问的 URL（如 `https://xxx.up.railway.app`）。
2. 构建前端时执行：  
   `VITE_API_BASE_URL=https://你的后端URL npm run build`  
   （URL 不要末尾 `/`）。
3. 后端环境变量中设置：  
   `CORS_ORIGIN=https://你的前端页面域名`。
4. 将 `dist` 部署到静态托管，用浏览器打开前端页面，尝试登录 / AI 对话，确认请求能到达后端且无跨域报错。

按以上步骤即可实现前后端分别上线。

## 五、静态托管时不要暴露数据库（重要）

若前端**纯静态托管**（如只把 `dist` 部署到 GitHub Pages，不跑后端），则 **`public/` 里所有文件在构建时都会被拷到 `dist` 并一起部署**。  
也就是说：**数据库（如 `competitor_data.db`、`wechatdouyin.db`）和敏感配置（如 `auth-config.json`）会变成静态资源，任何人只要知道地址就能直接下载。**

**已做的防护**：  
- 使用仓库里的 **`npm run deploy`**（即 `predeploy` + `deploy`）时，会在上传前执行 **`scripts/strip-sensitive-from-dist.js`**，从 `dist` 里删除这些敏感文件再推送到 gh-pages，避免被直接下载。  
- 敏感列表与后端 `/api/data` 白名单一致（如各 `.db`、`周报谷歌表单.csv`、`report_documents.json`、`auth-config.json` 等），可按需在脚本中增删。

**建议**：  
- **只做静态托管**：务必用 **`npm run deploy`** 部署，不要手动把带敏感文件的 `dist` 推上去；若需在静态站使用这些数据，应改为部署后端，数据只放在后端，通过登录后 `/api/data` 访问。  
- **前后端分离**：敏感数据只保留在后端服务器，前端静态站不包含任何 `.db` 或敏感 json/csv，所有数据请求走 `VITE_API_BASE_URL` 指向的后端并鉴权。

## 六、预生产分支（staging）

在正式发布前，可以用「预生产分支 + 预生产环境」先验证，再合并到 main 发布。

### 1. 创建预生产分支

```bash
git checkout -b staging
git push -u origin staging
```

之后在 `staging` 上开发、自测，确认无误再合并到 `main` 并执行正式部署。

### 2. 预生产前端构建与部署

- 复制环境变量示例并填写预生产后端地址：
  ```bash
  cp .env.staging.example .env.staging
  # 编辑 .env.staging，填写 VITE_API_BASE_URL=https://你的预生产后端.up.railway.app
  ```
- 构建并部署到**单独分支**（不影响当前 gh-pages 生产）：
  ```bash
  npm run deploy:staging
  ```
  会执行：`build:staging`（读取 `.env.staging`）→ strip 敏感文件 → 推送到远程分支 `gh-pages-staging`。

### 3. 如何访问预生产前端

- **方式 A**：本仓库若只配置了一个 GitHub Pages 源（如 `gh-pages`），则 `gh-pages-staging` 分支默认不会单独成站。可再建一个仓库（如 `monitor-web-staging`），把本仓库的 `gh-pages-staging` 分支推过去，用该仓库的 GitHub Pages 作为预生产地址。
- **方式 B**：用 Vercel/Netlify 等连接本仓库的 `staging` 分支，构建命令设为 `npm run build:staging`，环境变量里配置 `VITE_API_BASE_URL`，用其提供的预览 URL 作为预生产前端。

### 4. 预生产后端

在 Railway（或其它平台）上单独建一个项目，部署同一套后端代码，用测试用环境变量（如测试用 OPENAI key、测试 CORS 等）。将该项目的公网 URL 填进 `.env.staging` 的 `VITE_API_BASE_URL`，再跑 `npm run deploy:staging` 即可让预生产前端连到预生产后端。
