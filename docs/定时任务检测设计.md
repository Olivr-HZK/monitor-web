# 定时任务检测设计

目标：每个定时任务跑完后，都能机器判断「有没有真的拉到数据」「数据是否完整」「下游是否可以使用」，而不是只靠日志和人工看 mtime。

本文覆盖两层：

- **单任务检测**：每个 cron 任务结束后，立刻检查自己的产物。
- **链路检测**：monitor-web 在源库校验、后端 `/api/data` 检查、推送前，汇总上游任务状态，决定继续、跳过或报警。

## 1. 总体原则

| 原则 | 说明 |
|------|------|
| 不只看 exit code | 脚本成功退出不等于数据正确入库。必须查目标日期、目标表、目标维度和记录量。 |
| 不只看 mtime | 文件今天变了不代表本期数据完整。mtime 只做第一道 freshness 检查。 |
| 每个任务产出状态文件 | 每个任务写 `latest.json` 和按日期归档的 `run_id.json`，方便总控读取。 |
| 数据检查靠业务规则 | 例如微信/抖音必须是两平台六榜，ST 周榜应有 10 个国家 × 2 平台 × Top100，竞品周报应覆盖目标周。 |
| 失败默认阻断下游 | 拉取或完整性失败时，不部署、不推送旧数据；人工救急需要显式开关。 |
| 检测可重复执行 | checker 必须只读，不改业务数据；同一天可多次重查。 |
| 状态可聚合 | 单任务状态用于生成一条总览消息：OK、WARN、FAIL、SKIP。 |

## 2. 推荐目录结构

```text
monitor-web/
  config/
    task_checks.yml                  # 任务注册表，定义每个任务的产物、期望日期、SQL 检查
  logs/
    task-status/
      sensortower-weekly/
        latest.json
        2026-05-11T073000.json
      wechat-douyin-weekly/
        latest.json
      monitor-chain/
        latest.json
    task-health-summary/
      2026-05-11.md
  scripts/
    cron/run_job.sh                  # 统一 cron 包装器：执行任务、记录开始/结束、加锁
    run_task_healthcheck.py           # 通用检测入口
    send_monitor_chain_status.py      # 发送状态摘要，已有同类脚本可扩展
```

已迁入 `pipelines/monitor-chain/` 的任务先由 `scripts/cron/run_job.sh` 管住日志、锁和退出状态；业务完整性仍由 `validate_monitor_chain_sources.py`、`check_monitor_api_data.py` 与 watchdog 读取 canonical DB 判断。

## 3. 状态文件格式

每个任务每次运行写一份 JSON：

```json
{
  "task_id": "wechat-douyin-weekly",
  "run_id": "2026-05-11T073000+0800",
  "schedule": "30 7 * * 1",
  "started_at": "2026-05-11T07:30:00+08:00",
  "ended_at": "2026-05-11T07:34:12+08:00",
  "status": "OK",
  "severity": "blocking",
  "target": {
    "report_date": "2026-05-11",
    "week_range": "2026-05-04~2026-05-10"
  },
  "artifacts": [
    {
      "path": "/Users/ggbond/lyb/monitor-web/data/databases/wechatdouyin.db",
      "mtime": "2026-05-11T07:34:08+08:00",
      "size_bytes": 1234567,
      "integrity": "ok"
    }
  ],
  "checks": [
    {
      "name": "six_chart_groups",
      "status": "OK",
      "actual": {
        "dy/bestseller": 20,
        "dy/new_games": 20,
        "dy/popularity": 20,
        "wx/bestseller": 10,
        "wx/casual_play": 17,
        "wx/popularity": 16
      }
    }
  ],
  "summary": "微信/抖音 2026-05-04~2026-05-10 六榜齐，rank_changes=22",
  "log_path": "/Users/ggbond/lyb/monitor-web/logs/jobs/wechat_douyin_weekly.log"
}
```

状态枚举：

| 状态 | 含义 | 下游动作 |
|------|------|----------|
| `OK` | 数据拉取和完整性检查都通过 | 可继续 |
| `WARN` | 非关键项缺失，例如某个可选摘要为空 | 可继续，但状态摘要标黄 |
| `FAIL` | 关键数据缺失、DB 损坏、脚本失败 | 阻断下游 |
| `STALE` | 没有新数据或目标日期不匹配 | 阻断下游 |
| `SKIP` | 任务按规则不该在今天跑 | 不阻断 |
| `UNKNOWN` | 找不到状态文件或 checker 异常 | 默认按 FAIL 处理 |

## 4. 检测分层

### 4.1 运行层

每个 cron 任务都应记录：

- 开始时间、结束时间、耗时。
- exit code。
- Python/Node 版本。
- 最后 100 行日志摘要。
- 是否命中错误关键词：`Traceback`、`Error:`、`UnhandledPromiseRejection`、`HTTP 403`、`timeout`、`captcha`、`Permission denied`。

运行层只回答：脚本有没有正常跑完。

### 4.2 产物层

对文件或目录检查：

- 目标文件存在。
- mtime 晚于本次任务开始时间，或晚于当天 cutoff。
- 文件大小高于最低阈值。
- SQLite 执行 `PRAGMA integrity_check` 为 `ok`。
- 不残留临时边车文件：`*.db-wal`、`*.db-shm`、`*.tmp.*`。
- CSV/JSON 可解析，不是空文件。

产物层回答：文件有没有被写下来，是否可读。

### 4.3 业务层

对数据库或 CSV 内容检查：

- 目标日期或目标周存在。
- 记录数达到最低阈值。
- 平台、榜单、国家、公司等维度完整。
- 主键或唯一约束无异常重复。
- 关键字段非空，例如 `app_id`、`game_name`、`rank`、`company_name`、`report_content`。
- 本期数据不能完全等于上一期。可以用行数、hash、Top N app_id/game_name 对比。

业务层回答：数据是不是这次该拉的数据，量和维度是否合理。

### 4.4 下游层

对 monitor-web 这条链路还要检查：

- 四份 canonical DB 可读，生产后端 `/api/data/*.db` 能返回请求级 SQLite 快照，下载后的快照能通过 SQLite 校验。
- 本机 API 需要读取的 JSON 已生成。
- API 健康检查 200。
- 人工发布静态产物时，Pages 上不包含 `.db`。
- 推送 webhook 返回业务成功。
- sent marker 存在，避免重跑重复推送。

下游层回答：数据是否已经进入用户实际能看到的地方。

## 5. 任务级检测规则

### 5.1 微信/抖音小游戏周榜

| 项 | 规则 |
|----|------|
| 任务 | `wechat-douyin-weekly` |
| 频率 | 每周一 7:30 |
| 目标周期 | `report_date - 7` 到 `report_date - 1` |
| 产物 | `data/databases/wechatdouyin.db`；三榜 CSV 目录 |
| SQLite | `PRAGMA integrity_check = ok` |
| top20 完整性 | `top20_ranking` 中目标 `week_range` 必须有 6 个组合：`wx/popularity`、`wx/bestseller`、`wx/casual_play`、`dy/popularity`、`dy/bestseller`、`dy/new_games` |
| top20 数量 | 每个组合 `COUNT(*) > 0`；抖音通常应为 20，微信允许低于 20 但不应为 0 |
| 异动完整性 | `rank_changes` 目标周总数可以波动，但表必须可查询；monitor-web 集中链路当前按 `COUNT(*) > 0` 判定，否则 `FAIL`，避免空周报上线 |
| 旧入口防呆 | 发现只有 `popularity` 两个组合时直接 `FAIL`，提示疑似跑了旧单榜脚本 |
| 下游产物 | `public/ai热点/minigame_weekly_<week>.json` 必须在推送前生成 |

### 5.2 SensorTower 周榜

| 项 | 规则 |
|----|------|
| 任务 | `sensortower-weekly` |
| 频率 | 每周一 7:30 |
| 目标日期 | 周一当天 `report_date` |
| 产物 | `data/databases/sensortower_top100.db` |
| SQLite | `PRAGMA integrity_check = ok` |
| Top100 完整性 | `apple_top100` 和 `android_top100` 在目标 `rank_date` 各应接近 1000 条，标准为 10 国家 × 2 榜单 × Top100；最低阈值建议 950 |
| 异动完整性 | `rank_changes.rank_date_current = report_date` 记录数 `> 0` |
| 摘要完整性 | `weekly_top5_overview.rank_date = report_date` 必须存在；没有则 `WARN`，若推送依赖它则 `FAIL` |
| 元数据 | `weekly_metadata_changes.rank_date = report_date` 可为 0，但表需存在；作为 `INFO/WARN` |

### 5.3 SensorTower 我方产品日更

| 项 | 规则 |
|----|------|
| 任务 | `sensortower-us-free-daily` |
| 频率 | 每天 8:30 |
| 目标日期 | 今天或脚本参数对应日期 |
| 产物 | `data/databases/us_free_appid_weekly.db` 中 `app_ranks` / `weekly_summaries` 等我方产品记录 |
| freshness | DB mtime 晚于 8:30 任务开始 |
| 完整性 | 目标日期存在；被监控 app_id 集合均有本日记录或有明确缺失原因 |
| 合理性 | rank 为正整数；同一 app_id 同一天不重复；变化字段可解析 |
| 下游 | monitor-web 周一集中链路建议排在 8:45，确保这批日更已落库 |

### 5.4 竞品每日爬取

| 项 | 规则 |
|----|------|
| 任务 | `competitor-daily-scraper` |
| 频率 | 每天 7:30 |
| 目标日期 | 通常为昨天或脚本内部 fetch_date |
| 产物 | `data/databases/competitor_data.db` |
| SQLite | `PRAGMA integrity_check = ok` |
| 公司覆盖 | `company_tables_index` 中配置的公司表都应存在 |
| 数据覆盖 | 每个 `company_raw_data_*` 目标 `fetch_date` 有记录，或有显式空结果状态 |
| 平台覆盖 | 对每家公司配置的平台，目标日期应有记录；缺少核心平台为 `FAIL`，可选平台为 `WARN` |
| JSON 完整性 | `posts_json` 必须为合法 JSON；`posts_count` 与 JSON 数组长度大体一致 |

### 5.5 竞品周报

| 项 | 规则 |
|----|------|
| 任务 | `competitor-weekly-report` |
| 频率 | 每周一 7:40 |
| 目标周期 | 上周一到上周日，`end_date = report_date - 1` |
| 产物 | `weekly_reports` |
| 完整性 | 目标 `end_date` 至少有一条；建议覆盖核心公司清单 |
| 内容检查 | `report_content` 可解析为 JSON，且包含标题、评分、核心内容字段 |
| 去重 | `UNIQUE(company_name, start_date, end_date)` 不应冲突失败；若日志有 insert/update 错误为 `FAIL` |

### 5.6 monitor-web 源库校验与 API 连通性检查

| 项 | 规则 |
|----|------|
| 任务 | `monitor-chain` |
| 频率 | 每周一 8:45 |
| 前置 | `wechat-douyin-weekly`、`sensortower-weekly`、`competitor-weekly-report` 均为 `OK` 或允许的 `WARN` |
| 源库访问 | 四份 canonical DB 均存在；生产 `/api/data/*.db` 可生成 SQLite backup 快照，且下载快照 `PRAGMA quick_check = ok` |
| 业务校验 | 复用四库 checker，检查 canonical DB 的目标周期 / 目标日期 |
| 检查/推送 | cron 入口为 `sync_dbs_and_deploy.sh` 或 `check_monitor_chain.sh`；前者检查通过后推送，后者只检查 |
| Pages 安全 | 人工 deploy 时 `gh-pages` 不应包含 `.db`、`.sqlite`、`auth-config.json` |
| 推送 | 默认不推送；人工补发时不包含「我方产品变化 / 指定产品竞品变化」 |
| 状态 | 写 `logs/monitor_chain_last_status.md` 并推送摘要 |

### 5.7 其它热点/日报任务

对 tiktok、X、trustmrr、gaming、AI 工具等项目，建议统一套同样模型，但先按三类简单检查：

| 类型 | 检测重点 |
|------|----------|
| prepare/generate | 输出文件存在、目标日期正确、记录数高于阈值、内容可解析 |
| push | webhook 返回成功、sent marker 存在、同日不重复发 |
| cleanup/backup | 备份文件存在且大小合理；清理任务只检查 exit code 和日志错误 |

## 6. 调度方式

推荐每个 cron 通过统一 runner：

```cron
30 7 * * 1 /Users/ggbond/lyb/monitor-web/scripts/cron/run_job.sh wechat_douyin_weekly
```

`run_job.sh` 做三件事：

1. 记录 `started_at`、环境、命令。
2. 加锁执行任务并捕获 exit code。
3. 写 `logs/jobs/<job-id>.log` 和 `logs/jobs/<job-id>.last_status`。

业务数据是否完整由 checker 在集中链路里执行；后续若实现 `run_task_healthcheck.py`，可接在 `run_job.sh` 之后写更细的 JSON 状态。

再加一个总检查 cron：

```cron
15 9 * * * cd /Users/ggbond/lyb/monitor-web && ./scripts/check_monitor_chain.sh >> logs/task_healthcheck.log 2>&1
```

周一 `monitor-chain` 不等到 9:15，它在自己的集中链路脚本里先跑 blocking healthcheck。9:15 的总检查负责兜底和跨项目汇总。

## 7. 告警策略

| 级别 | 触发 | 通知 |
|------|------|------|
| P0 | monitor-chain API 不通、四库关键数据缺失 | 立即飞书 |
| P1 | 上游任务 FAIL 或 ST/微信/竞品关键维度缺失 | 立即飞书 |
| P2 | 可选摘要缺失、数量低于历史均值但不为 0 | 汇总通知 |
| P3 | 日志清理、备份轻微异常 | 只写状态文件 |

告警内容必须包含：

- task_id 和状态。
- 目标日期/周期。
- 失败的具体检查项。
- 实际数量和期望数量。
- 日志路径。
- 建议重跑命令。

## 8. 分阶段落地

### 第一阶段：monitor-web 管住关键链路

- 扩展现有 `validate_monitor_chain_sources.py`，拆成通用 checker。
- 用 `scripts/cron/run_job.sh` 给微信/抖音、ST 周榜、竞品周报、monitor-chain 写统一 log 和 last_status。
- `sync_dbs_and_deploy.sh` 读取 canonical DB 和后端快照，失败时阻断；细粒度 task status 可作为下一阶段补充。

### 第二阶段：把业务状态写细

- 在 `run_job.sh` 或各 pipeline 尾部接入 task status JSON。
- 每个上游任务跑完立即写 `latest.json`。
- monitor-web 不再只查 DB，也查上游任务自己的状态。

### 第三阶段：纳入所有本机 cron

- 把 tiktok、X、trustmrr、gaming、AI 工具等任务加入 `task_checks.yml`。
- 每天 9:15 发一条全量健康摘要。
- 对 push 类任务统一 sent marker。

### 第四阶段：趋势和异常阈值

- 保存每次检测的 row count 和耗时。
- 用最近 4 到 8 次的中位数做动态阈值。
- 发现“突然从 1000 条变 200 条”这类情况，哪怕不为 0 也报 WARN/FAIL。

## 9. 最小可行实现

最先实现这四个文件即可：

```text
scripts/cron/run_job.sh
scripts/validate_monitor_chain_sources.py
scripts/check_monitor_api_data.py
scripts/send_monitor_chain_status.py
docs/定时任务检测设计.md
```

`task_checks.yml` 负责声明任务，示例：

```yaml
tasks:
  wechat-douyin-weekly:
    project_root: /Users/ggbond/lyb/monitor-web/pipelines/monitor-chain/wechat-douyin
    schedule: "30 7 * * 1"
    kind: weekly
    report_date: today
    artifacts:
      - path: /Users/ggbond/lyb/monitor-web/data/databases/wechatdouyin.db
        type: sqlite
        freshness: after_start
    checks:
      - type: sqlite_integrity
      - type: wechat_douyin_six_charts
        week_range: previous_week
      - type: no_legacy_single_chart
```

这套设计落地后，cron 的成功标准会从“命令执行过”变成“对应日期的数据完整、可读、可发布、可推送”。
