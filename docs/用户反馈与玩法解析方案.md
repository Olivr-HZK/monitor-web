# 用户反馈与玩法解析方案

## 当前流程简述

1. **企业微信**：通过自定义机器人 Webhook **单向推送**周报（Markdown），用户点击链接进入监测汇总网站。
2. **网站**：用户可查看微信/抖音小游戏排行榜、SensorTower 周报等；玩法解析来自 `wechatdouyin.db` 的 `games.gameplay_analysis`，在「新游戏/新玩法」列表中点击条目进入报告详情查看。
3. **限制**：企业微信自定义机器人**不能接收用户消息**，只能发送。因此用户无法在企微里直接「回复某游戏名申请玩法解析」。

---

## 一、如何接收用户反馈

### 方式 1：网站内「申请玩法解析」（推荐，已实现）

- 在**排行榜**或**玩法详情页**为每个游戏提供「查看玩法」入口；若该游戏暂无玩法解析，则显示「申请玩法解析」按钮。
- 用户点击后提交到后端接口（如 `POST /api/feedback/gameplay-request`），后端将申请写入本地文件或数据库，并可选择：
  - 发一条飞书/企业微信消息通知你：「用户 xxx 申请了《游戏名》的玩法解析」。
- **优点**：闭环在站内，用户从企微点进链接后即可操作；你能在后台或群内收到明确申请列表。

### 方式 2：企业微信内接收（需额外开发）

- 企业微信要**接收用户消息**，需使用「接收消息」型应用或群机器人回调，配置 API 接收用户 @ 或私聊内容，再解析「想要 XX 游戏玩法解析」并落库/通知。
- **优点**：用户不用离开企微。**缺点**：需要企业微信应用配置与回调服务开发，工作量较大。

### 方式 3：飞书/多维表格/表单

- 在周报或网站中放一个「申请玩法解析」链接，指向飞书多维表格、金数据等表单，字段：游戏名、平台、备注。
- **优点**：零后端开发，你直接在表格里看反馈。**缺点**：用户需多一步跳转，且与站内体验割裂。

---

## 二、如何「实时生成并返回」玩法解析

### 选项 A：实时生成（AI）

- 用户点击「申请玩法解析」或「生成玩法」时，后端调用大模型 API，根据游戏名（及可选：平台、简介）生成玩法解析文案，再：
  - **立即返回**：接口返回 Markdown，前端展示；可选同时写入 `wechatdouyin.db` 的 `games.gameplay_analysis`，下次直接读库。
  - **异步返回**：先返回「生成中」，后台任务生成完成后写入 DB，再通过企业微信 Webhook 推送「《某某》玩法解析已生成」+ 链接。
- **前提**：配置大模型 API Key（如 OpenAI/国内大模型），并在后端实现调用与结果格式化（与你现有 `gameplay_analysis` JSON 结构一致更佳）。

### 选项 B：人工/异步生成

- 用户申请后，仅做**记录**（如写入 `gameplay_requests.json` 或 DB），你或运营在后台看到申请列表后，人工撰写或批量用脚本调 AI 生成，再写入 `games.gameplay_analysis` 并更新 DB 文件。
- 生成完成后，可选：用现有企业微信 Webhook 推送「《某某》玩法解析已上线，点击查看」+ 链接。
- **优点**：不依赖实时 API，质量可控。**缺点**：非实时，需你主动处理申请列表。

---

## 三、本仓库已实现部分

- **排行榜入口**：微信/抖音小游戏榜单中，游戏名可点击，跳转到「玩法解析」详情页（`/gameplay/wechat_douyin/游戏名`）。
- **玩法详情页**：若该游戏在 `wechatdouyin.db` 的 `games` 表中有 `gameplay_analysis`，则展示；否则展示「暂无玩法解析」并显示「申请玩法解析」按钮。
- **申请接口**：`POST /api/feedback/gameplay-request`，请求体 `{ "gameName": "游戏名", "source": "wechat_douyin", "remark": "可选备注" }`。后端将申请追加到本地文件（如 `data/gameplay_requests.json`），便于你查看与处理。
- **可选**：在后端写入申请后调用飞书/企业微信 Webhook，给你发一条「用户申请了《某某》玩法解析」的通知（需在 `.env` 配置对应 Webhook）。

## 四、建议流程（结合你当前架构）

1. **接收反馈**：继续使用「网站内申请」为主；在周报或企微推送文案里提示「需要某游戏玩法解析可点链接进入排行榜 → 点游戏名 → 申请玩法解析」。
2. **生成**：优先用**异步**（申请落库 → 你或脚本批量生成 → 写入 DB）；若后续要「实时生成」，再在后端加一层大模型调用与写入 DB，前端在申请后轮询或 WebSocket 取结果。
3. **返回给用户**：生成后更新 `wechatdouyin.db`，用户再次打开该游戏玩法页即可看到；可选再发一条企微推送「《某某》玩法已更新」+ 链接，提升触达。

## 五、环境变量（可选通知）

若希望后端在收到「申请玩法解析」时自动发通知：

- `FEISHU_WEBHOOK_URL`：飞书机器人 Webhook，用于发送「申请」提醒。
- `WECOM_WEBHOOK_URL_REAL` 或 `WECOM_WEBHOOK_URL`：企业微信机器人 Webhook，用于发送「申请」提醒。

未配置时，申请仍会写入本地文件，仅不会推送消息。

## 六、申请玩法解析 - 完整数据流（提了需求后怎么走）

用户点击「申请玩法解析」后的流程如下：

```
用户点击「申请玩法解析」
    ↓
前端 POST /api/feedback/gameplay-request
    body: { gameName, source: "wechat_douyin", remark }
    ↓
请求发到「当前访问的站点」的 /api 路径
    ↓
┌─────────────────────────────────────────────────────────────────┐
│ 情况 A：有后端（Node 服务在跑）                                    │
│   - 开发：Vite 把 /api 代理到 localhost:3001，后端收到请求          │
│   - 生产：Nginx/同机部署把 /api 转到 Node，后端收到请求             │
└─────────────────────────────────────────────────────────────────┘
    ↓
后端 server.js 的 app.post('/api/feedback/gameplay-request')
    ↓
1. 校验 gameName 非空
2. appendGameplayRequest() → 追加到 data/gameplay_requests.json
3. notifyGameplayRequest() → 若配置了 FEISHU_WEBHOOK_URL / WECOM_* 则发一条通知
4. 返回 200 { ok: true }
    ↓
前端收到 200 → 显示「已收到您的申请」
```

**为什么会出现 404 / 提交失败？**

```
┌─────────────────────────────────────────────────────────────────┐
│ 情况 B：无后端（纯静态站点）                                        │
│   - 开发：只跑了 npm run dev，没有同时跑 node server/server.js     │
│   - 生产：部署在 GitHub Pages / 纯静态托管，没有 Node 服务           │
└─────────────────────────────────────────────────────────────────┘
    ↓
请求发到静态服务器（如 GitHub Pages）
    ↓
静态服务器没有 /api/* 路由 → 返回 404 Not Found
    ↓
前端收到 404 → 显示「提交失败：Not Found」
```

**要让「申请玩法解析」真正可用，必须让请求能到达 Node 后端：**

| 环境 | 做法 |
|------|------|
| **本地开发** | 终端 1：`npm run dev`；终端 2：`node server/server.js`。Vite 会把 `/api` 代理到 3001。 |
| **生产** | 把 Node 服务部署到能公网访问的机器/容器，前端请求的域名要指向该服务，或同域下 Nginx 把 `/api` 反代到 Node。 |
| **仅静态部署（如 Google Pages / GitHub Pages）** | 见下方「托管在 Google Pages 时如何获取」：要么配远程后端地址，要么用表单/复制兜底。 |

申请落库后的**后续流程**（你这边处理）：

1. 打开 `data/gameplay_requests.json` 查看新申请（或收飞书/企微通知）。
2. 人工或脚本为该游戏生成玩法内容，写入 `wechatdouyin.db` 的 `games` 表、`gameplay_analysis` 字段。
3. （可选）企微推送「《某某》玩法解析已上线」+ 链接。

## 七、托管在 Google Pages（或其它静态站）时如何获取用户申请

前端部署在 **Google Pages / GitHub Pages** 时，页面本身没有后端，请求 `/api/...` 会发到静态站 → 404。要让用户在托管页上点击「申请玩法解析」时你能收到，有两种做法。

### 做法一：后端单独部署 + 前端指向该地址（推荐）

1. **把 Node 后端部署到能公网访问的服务**  
   任选一种即可：
   - **Vercel**：用 Vercel 的 Node 运行时部署 `server/`，得到 `https://xxx.vercel.app`
   - **Railway / Render / Fly.io**：同上，得到 `https://xxx.railway.app` 等
   - **自己的服务器 / 云主机**：跑 `node server/server.js`，用 Nginx 反代，得到 `https://api.你的域名.com`

2. **前端构建时指定后端地址**  
   在项目根目录 `.env` 或构建命令里设置：
   ```bash
   VITE_API_BASE=https://你的后端地址
   ```
   例如：
   ```bash
   VITE_API_BASE=https://monitor-api.vercel.app
   ```
   然后执行：
   ```bash
   npm run build
   ```
   构建出的前端里，所有「申请玩法解析」请求会发到 `https://你的后端地址/api/feedback/gameplay-request`，不再发到 Google Pages。

3. **后端开启 CORS**  
   本项目 `server/server.js` 已默认加 CORS 中间件，允许任意来源调用（`Access-Control-Allow-Origin: *`）。若生产环境要限制为仅你的静态站，可在后端环境变量中设置 `CORS_ORIGIN=https://你的静态站域名`。

4. **结果**  
   用户在 Google Pages 上点击「申请玩法解析」→ 浏览器请求你部署的后端 → 后端写入 `data/gameplay_requests.json` 并可选发飞书/企微通知 → **你就能获取到**。

### 做法二：不用自建后端，用第三方「接住」提交

不部署 Node 时，可以让点击行为跳转到别处，由第三方把结果给你：

- **Google 表单**：做一个表单，字段「游戏名」「备注」。玩法页上「申请玩法解析」改为打开该表单链接（可用 URL 参数预填游戏名）。用户提交后，你在 Google 表格里看到或收到邮件。
- **Formspree / Getform**：表单 `action` 填他们提供的 URL，他们代收 POST 并邮件/Webhook 给你。
- **复制兜底（已实现）**：当前 404 时页面会提示「复制申请内容」发给管理员，用户粘贴到企微/飞书给你。

总结：**用户在托管页点击后你能获取到 = 要么请求落到你部署的后端（做法一），要么落到表单/邮件/企微（做法二）。**

## 八、使用说明

- **排行榜**：打开「休闲游戏 → 微信/抖音小游戏」页，点击任意游戏名即可进入该游戏的玩法解析页。
- **玩法解析页**：若数据库中有该游戏的玩法内容则直接展示；否则显示「申请玩法解析」按钮，点击后提交到后端并提示「已收到您的申请」。
- **后端**：`POST /api/feedback/gameplay-request` 需在**后端模式**下启动 Node 服务（`node server/server.js` 或生产部署）后才可用；申请会追加到项目根目录下 `data/gameplay_requests.json`（该目录已加入 `.gitignore`）。
- **若当前环境无后端（404）**：页面会提示并支持「复制申请内容」发给管理员或通过其他渠道反馈。
- **托管在 Google Pages 时**：构建时设置 `VITE_API_BASE=https://你的后端地址`，并把后端单独部署并开启 CORS，即可在托管页点击时收到申请；详见上文「七、托管在 Google Pages 时如何获取」。
