# 监测链定时任务规范（monitor-web + 依赖库）

本文档只约束 **本仓库（monitor-web）** 与 **由 API 后端直连读取的四份上游数据库** 相关的定时任务，用于在多台机器、多人协作时保持**同一套约定**。
**不**覆盖 TrendRadar、tiktok-rader、gaming-daily-report、trustmrr 等与监测链无直接数据依赖的项目（那些任务可单独维护）。

详细时间表与日志路径见 **[定时任务说明.md](./定时任务说明.md)**。
每个任务的数据拉取与完整性检测设计见 **[定时任务检测设计.md](./定时任务检测设计.md)**。

---

## 1. 范围（监测链）

| 角色 | 路径 / 仓库 |
|------|-------------|
| 站点与集中链路脚本 | `monitor-web/`（本仓库） |
| SensorTower 主库 | `~/lyb/sensortower-/data/sensortower_top100.db` |
| 竞品社媒库 | `~/lyb/Olivr-competitor-monitor/db/competitor_data.db` |
| 微信/抖音小游戏库 | `~/lyb/wechat-mini-game-ranking-post/data/wechatdouyin.db` |
| SensorTower 我方产品库 | `~/lyb/sensortower-/data/us_free_appid_weekly.db`（优先）或同目录 `us free app id.db` |

**线上数据入口**：前端走 `VITE_API_BASE_URL`，后端 `/api/data/*.db` 根据 `backend/config.py` 的 `DATA_SOURCE_DB_PATHS` 直连上游源库，并按请求返回 SQLite backup 快照；`public/` 只保留 JSON/CSV/MD/图片等非 DB 静态产物。

---

## 2. 调度方式标准（监测链**只认 crontab**）

| 类型 | 标准 |
|------|------|
| **监测链内**所有「按点跑批」的任务（含微信周榜、ST、竞品、monitor-web 集中校验） | **一律用 `crontab`**，见 **[scripts/monitoring-chain.cron.fragment.txt](../scripts/monitoring-chain.cron.fragment.txt)** 可粘贴片段 |
| **曾用 LaunchAgent 的微信周榜** | **迁移到 cron 后必须卸载 plist**，避免同一脚本跑两次（见下文「9. 迁移」） |
| **OpenClaw、guru-monitor、常驻网关** 等 | 仍可用 LaunchAgent，**不属于**监测链，不要求与本文统一 |

**原则**：监测链**不再**把「周榜 / 日爬 / 同步」拆在 cron 与 LaunchAgent 两处；统一进 **一份 crontab 片段**（或你本机 crontab 中等价行），便于 `crontab -l` 一眼看完。

**包装脚本**：上游仓库已有 `cron_run_weekly.sh`、`cron_run_us_free_daily.sh` 等，在脚本内补齐 `PATH`、日志；监测链 cron 行尽量 **cd 到项目目录再执行**，与 LaunchAgent 的 `WorkingDirectory` 等价。

## 3. 时间阶梯（周一发布日，建议）

以下时间为「约定顺序」，本机若需微调，只改 crontab，**但须保持先后关系**（上游先写完库 → 再跑 `sync_dbs_and_deploy.sh` 做后端检查与推送）。

| 时间（示例） | 环节 |
|--------------|------|
| 7:30 | 微信/抖音周榜三榜入库（人气 + 畅销 + 微信畅玩/抖音新游）、ST 周工作流、竞品日爬（可并行） |
| 7:40 | 竞品周报工作流（写库） |
| 8:30 | ST「我方产品」日更 |
| 8:45 | **monitor-web** `sync_dbs_and_deploy.sh`（源库业务校验 → 生成小游戏周报 JSON → 探测生产 API 并下载四份 `/api/data/*.db` 快照做 SQLite 校验 → 通过后推送三条核心周报；不拷 DB，cron 设置 `SYNC_SKIP_DEPLOY=1` 不额外 deploy） |
| 8:50 / 9:50 | 微信/抖音周榜完整性补跑：若目标周六榜或 `rank_changes` 不完整，再自动跑一次 |

`sync_dbs_and_deploy.sh` 默认 **`SYNC_CUTOFF_HOUR=7`**，与 **8:45** 跑批对齐；若改同步时间，需同步评估 cutoff。

## 4. 本仓库唯一入口

| 动作 | 标准做法 |
|------|----------|
| 校验四份源库、生成本机 API 可读产物、探测 API 数据链路、检查通过后推送 | **只**通过 **`sync_dbs_and_deploy.sh`**。API 离线或 `/api/data/*.db` 快照读取失败都会默认失败并中止推送；cron 设置 `SYNC_SKIP_DEPLOY=1`，不额外 deploy、不发布静态备用 `.db` |
| 上游数据库备份 | 由各项目自己的 cron 成功后执行：`sensortower-/scripts/backup_sqlite_db.sh`、`wechat-mini-game-ranking-post/scripts/backup_sqlite_db.sh`、`Olivr-competitor-monitor/scripts/backup_sqlite_db.sh` |
| 向 GitHub Pages 发布 | **`deploy:api`**（无 `.db`），由 `sync_dbs_and_deploy.sh` 触发，走 **`scripts/deploy.sh`**；需 `GIT_SSH_COMMAND`，见 `cron-deploy-GitHub认证配置.md` |

**不推荐**：再把上游 `.db` 复制到 `monitor-web/public` 作为生产数据源。生产读取应以 API 直连源库为准。

## 5. crontab 书写标准（本仓库这一条）

```cron
PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin
45 8 * * 1 /bin/bash -c 'cd /Users/你的用户名/lyb/monitor-web && SYNC_SKIP_DEPLOY=1 ./scripts/sync_dbs_and_deploy.sh >> logs/sync_dbs_cron.log 2>&1'
```

- `PATH`：`node`/`npm` 须在 PATH 中（Homebrew 常见路径见上）。
- 使用 **绝对路径**；`cd` 到仓库根再执行脚本。
- 日志落到 **本仓库 `logs/`**，便于与 `sync_dbs_and_deploy_YYYY-MM-DD.log` 对照。

## 6. 环境与依赖标准

| 项 | 要求 |
|----|------|
| Git / gh-pages | 按 **`docs/cron-deploy-GitHub认证配置.md`** 配置 SSH，保证 **`deploy:api`** 能非交互推送 |
| Python 推送脚本 | 建议在 `monitor-web` 下维护 **`.venv`**（`pip install -r requirements.txt`）；`sync_dbs_and_deploy.sh` 若存在 `.venv` 会自动 `activate` |
| 机密 | 仅 **`monitor-web/.env`**（或系统环境变量），**不**写入 crontab 明文 |

`sync_dbs_and_deploy.sh` 会优先使用 `monitor-web/.venv/bin/python`，并把该解释器用于校验、生成产物与可选手动推送；如需强制指定，设置 `SYNC_PYTHON_BIN=/path/to/python`。
默认 cron 会在后端与 `/api/data` 四库快照检查通过后，推送三条核心周报：SensorTower、竞品社媒、微信/抖音。人工手动补发时，monitor-web 默认不发送「我方产品变化 / 指定产品竞品变化」。

源库等待超时默认中止，避免发布旧数据。临时救急才设置 `SYNC_ALLOW_STALE_SOURCES=1`，并应人工确认四库内容。

API-only 模式下不再自动发布含 `.db` 的静态备用；若 API 不通，应先恢复后端/Cloudflare，再重跑集中链路。

本机 API 可用 LaunchAgent 保活，模板与安装脚本见 **[API LaunchAgent 运维.md](./API%20LaunchAgent%20运维.md)**。

## 7. 文档维护

- 本规范 **只描述原则与推荐默认值**；**本机实际 crontab 行**以 `crontab -l` 为准，变更后请同步 **[定时任务说明.md](./定时任务说明.md)** 中的时间表与示例。
- **监测链片段**以仓库内 **[scripts/monitoring-chain.cron.fragment.txt](../scripts/monitoring-chain.cron.fragment.txt)** 为模板，改时间时优先改该文件再同步到本机 crontab。

## 8. 与「其它项目」的边界

以下不属于本规范范围，**不要**写进本仓库的监测链标准里，除非明确接入 `public/`：

- 热点 / AI 日报（`run_reports.sh`）若仅共用 Webhook，可单独 cron，与四库同步解耦。
- 若你希望把「全站所有定时任务」也纳入一份总表，建议在 **个人笔记或独立运维仓库** 维护，避免与监测链混淆。

## 9. 从 LaunchAgent 迁到 cron（微信周榜）

原先若使用 **`com.wechat.minigame.weekly_scrape.plist`**（每周一 7:30），与监测链统一后请按顺序操作：

1. 将 **[scripts/monitoring-chain.cron.fragment.txt](../scripts/monitoring-chain.cron.fragment.txt)** 里「微信/抖音」主任务与补跑任务并入本机 `crontab`（或确认已有等价行）。主入口应为 `weekly_wx_three_charts_scrape_and_import.sh`，补跑入口应为 `rerun_weekly_wx_three_charts_if_needed.sh`。
2. **卸载**旧 LaunchAgent，避免重复执行：
   ```bash
   launchctl bootout gui/$(id -u) ~/Library/LaunchAgents/com.wechat.minigame.weekly_scrape.plist 2>/dev/null || true
   launchctl unload ~/Library/LaunchAgents/com.wechat.minigame.weekly_scrape.plist 2>/dev/null || true
   ```
   （任选一条成功即可；不同 macOS 版本命令略有差异。）
3. **可选**：将 plist **移走或改名备份**，例如 `com.wechat.minigame.weekly_scrape.plist.disabled`，防止登录时再次被加载。
4. 下周一 7:30 后检查 `wechat-mini-game-ranking-post/logs/weekly_scrape_import.log` 是否有新输出；若主任务失败，8:50/9:50 补跑会写入 `wechat-mini-game-ranking-post/logs/weekly_scrape_rerun.log`。

**注意**：`cron_run_weekly.sh`（ST）与微信周榜同为 **周一 7:30** 是允许的；cron 会分别启动多个任务。若某脚本对「同分钟多任务」敏感，再把其中一条顺延 1～2 分钟并更新 fragment 文件。
